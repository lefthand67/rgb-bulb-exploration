## 2A. Prerequisite bugfix — stale vertical centering («текст начинается с середины слайда») — DO THIS FIRST

> **Not optional, not part of the new slide.** This is a pre-existing, reproducible, deck-wide layout bug. The new switch slide would inherit it (the switch, like the cups, is injected by `initSlide()`). Fix it before building the slide, and ship it together with this plan.

### 2A.1 Symptom (as reported)
On the affected slides the text block appears to start around the middle of the slide, and the bottom of the content is cut off — «как будто произошло смещение». Resizing the window (or rotating the device) briefly snaps the content back to its correct position.

### 2A.2 Root cause (measured, not guessed)
reveal.js 6 does **not** center slides with CSS flexbox — it centers them in JavaScript (`layout()`) by measuring each visible section and writing an inline `top`:

```js
// node_modules/reveal.js/dist/reveal.mjs (layout())
section.style.top = Math.max((slideHeight - section.scrollHeight) / 2, 0) + "px";
```

That measurement happens **once**, during `Reveal.initialize()` (and again only on `resize`). Our `main.js` then mutates the DOM **after** that pass:

- `Reveal.on('ready')` → `initSlide()` → `createBulb()` / `createLightMix()` / cups are inserted;
- `Reveal.on('slidechanged')` → `initSlide()` → the same for the slide being entered.

The section grows, but its stored `top` is never recomputed. Content is therefore pushed **down** by roughly `(newHeight − oldHeight)/2` and clipped at the bottom by the `max-height: 100%; overflow: hidden` rule on `section` (`app/src/css/theme.css`).

Measured with headless Firefox at 1280×800 on the packaged `web/index.html`: section `scrollHeight` vs the inline `top` reveal had stored (correct centering = `(720 − scrollHeight) / 2`):

| Slide | content `scrollHeight` | stored `top` | correct `top` | verdict |
|---|---|---|---|---|
| 1 «Твоя умная лампочка» | 421 | 141 | 149.5 | ✅ ok |
| 2 «Три чашки света» | 333 | 186.5 | 193.5 | ✅ ok |
| 3 «Цветовая лаборатория» (cups injected) | 620 | 205 | 50 | ❌ **+155 px too low, clipped** |
| 4 «Одна чашка» | 270 | 219.5 | 225 | ✅ ok |
| 5 «Две чашки» | 226 | 242 | 247 | ✅ ok |
| 7 «Разрушители мифов» | 512 | 93.5 | 104 | ✅ ok |
| 8 «Найди такой цвет» (cups injected) | 637 | 275 | 41.5 | ❌ **+233 px too low, clipped** |
| 9 «Что мы узнали» | 487 | 106.5 | 116.5 | ✅ ok |

Dispatching a single `window` `resize` event (which makes reveal re-run `layout()`) fixes the affected slides on the spot — e.g. slide 3 becomes `top=37px` vs `expected=37px`, slide 8 becomes `28.5px` vs `expected=29px`. **That is the proof of both the root cause and the fix.**

### 2A.3 Two contributing triggers (fix both)
1. **Dynamically injected widgets (confirmed).** Slides 0, 3 and 8 (and the new switch slide) mount bulbs/cups/canvases in `initSlide()` *after* reveal's layout pass. Their stored `top` was measured while the mount points were still empty. This is the visible, reproducible defect.
2. **Late web-font load (latent).** `app/src/css/theme.css` `@import`s Comfortaa/Nunito. If the fonts finish loading *after* the first layout, every section's text metrics (and therefore `scrollHeight`) change, leaving **all** sections stale. In the packaged single file the fonts are `data:` URLs and usually settle in time, but on the dev server or a slow machine this can hit every slide — which matches the «all slides» wording of the report. `document.fonts.ready` must trigger a relayout.

### 2A.4 Required fix
**`app/src/js/main.js` — re-run reveal's layout after every DOM change that can alter a section's height.**

```js
// reveal.js centers a section by writing an inline `top` from its scrollHeight.
// Any DOM mutation after that pass leaves the top stale → the slide is pushed
// down and clipped. Re-run the layout whenever we change the DOM.
function refreshSlideLayout() {
  Reveal.layout();
  // A second pass on the next frame catches widgets that settle asynchronously
  // (SVG sizing, canvas, images).
  requestAnimationFrame(() => Reveal.layout());
}

Reveal.on('ready', event => {
  initSlide(event.currentSlide);
  refreshSlideLayout();
});

Reveal.on('slidechanged', event => {
  cleanupComponents();
  initSlide(event.currentSlide);
  refreshSlideLayout();
});

// Fonts change text metrics (and therefore section heights) after first paint.
if (document.fonts && document.fonts.ready) {
  document.fonts.ready.then(() => Reveal.layout());
}
```

**Plus a catch-all `ResizeObserver`** (recommended) so any later height change — a bulb readout, a resizing canvas, a future widget — is self-healing:

```js
let layoutQueued = false;
const relayout = () => {
  if (layoutQueued) return;
  layoutQueued = true;
  requestAnimationFrame(() => { layoutQueued = false; Reveal.layout(); });
};
const sectionObserver = new ResizeObserver(relayout);
function observePresentSlide(slide) {
  sectionObserver.disconnect();
  if (slide) sectionObserver.observe(slide);
}
// call observePresentSlide(event.currentSlide) inside ready/slidechanged, AFTER initSlide()
```

Guard rails: `Reveal.layout()` only writes `top` (never `height`), so the observer cannot loop; still debounce with the `layoutQueued` flag + `requestAnimationFrame`. Add `sectionObserver.disconnect()` to the teardown path if the deck is ever re-initialised.

### 2A.5 Keep or relax `max-height: 100%; overflow: hidden`?
- **Keep it** for safety (it stops content spilling onto neighbouring slides), but only *after* §2A.4 makes centering correct.
- Independently, every slide must still *fit*. If a slide is genuinely taller than 720 px after the fix, that is a content-fitting task (shrink that slide's type/margins), tracked by the existing «no clipped content» acceptance item. Never use `overflow` to hide a layout bug.
- Do **not** remove `max-height` as a «fix»: that would only make the shifted content spill out visibly instead of being cut.

### 2A.6 Optional — do we even want vertical centering?
reveal's default is `center: true`, so short slides have empty space above and below and the text sits in the middle. If the desired look is *content pinned near the top*, set `center: false` in `Reveal.initialize()` — a one-line change, orthogonal to §2A.4. **Recommendation:** keep `center: true` (it is the deck's design and matches the reference plans) and fix the stale-layout bug instead. Confirm with the parent (see §15, Open questions).

### 2A.7 Verification (reproduce the measurement)
1. `npm run package`, serve `web/` (or run `npm run dev`).
2. In the browser console, on each slide compare `getCurrentSlide().style.top` with `(720 - getCurrentSlide().scrollHeight) / 2` — they must be equal (±1 px) on **every** slide, including 0, 3 and 8, **without** resizing.
3. Headless variant used to produce §2A.2: load the page with `#/3`, then in the load handler call `window.dispatchEvent(new Event('resize'))` and read the values; before the fix they disagree, after the fix they agree.
4. Resize the window while on a slide: the content must not jump to a different vertical position.

### 5.2 The light switch (`data-light-switch`)
- A real `<button role="switch">` (focusable, announces state) — **not** a div.
- One click/tap toggles **between exactly two states**: `off → {0,0,0}` and `on → {255,255,255}`. (White at full brightness is the clearest "ярче всего" and matches the myth-buster slide's `255,255,255` example.)
- Visual: pill/cassette toggle with a sliding knob; ON position shows «Вкл», OFF shows «Выкл»; the switch itself glows warm-white when ON.
- The button is a **≥ 56×56 px** touch target, with a visible focus ring.
- The toggle is **idempotent from the store**: the UI reads state from the store subscription, never from a local boolean, so programmatic changes (future reuse) stay in sync.

### 5.3 The bulb (`data-bulb-switch`)
- Reuse `createBulb({ mountEl, store })` unchanged.
- Store starts at `{ r: 0, g: 0, b: 0 }`.
- Optionally enlarge the bulb via the mount wrapper's CSS (`.switch-bulb { width: 260px }`), not by touching `bulb.js`.
- The `rgb()`/`#hex` readout already exists inside the component; keep it (it reinforces `rgb(0,0,0)` ↔ `rgb(255,255,255)`).

### 5.4 The 256-step ladder (`data-steps-scale`) — the "0 counts" proof
- A horizontal track with a marker that sits at **0** (far left) or **255** (far right); labels `0` and `255` are pinned to the ends.
- The track is rendered with **256 tiny ticks** (via `repeating-linear-gradient`, not DOM nodes) so the child can *see* individual steps; every 16th tick is slightly longer (`0, 16, 32 … 240, 255`). A magnified `1×256` micro-strip may reuse the existing `createStrip1D` from `app/src/js/grid2d.js` if desired, but that is **not required**.
- The pill **«256 шагов (и 0 — тоже шаг!)»** sits under the track whenever the slide is visible (not only after a fragment), because it is the takeaway.
- **Optional secondary affordance (recommended, keep it clearly below the switch):** a tiny «Шаг –›» stepper with `−1 / +1` buttons (or ← / → when focused) so a curious child can walk the ladder. Default copy: «Между ними — ещё **254** яркости.» If included, it must reuse `dragValue`/`clamp` helpers and must **not** steal Reveal's ← / → unless the scale is focused (same capture rule as the cups, §6.3). Mark cuttable if the slide gets busy.

### 5.5 Fragments & timing
- Only **two** fragments on this slide: the «Нажми на выключатель» cue (optional; could be static) and the aha sentence. The ladder itself is static so the child always has something to compare against.
- On slide enter, do **not** auto-animate the bulb; let the child discover the switch.

### 5.6 Slide 2 cleanup (required)
Delete the moved `<p class="fragment">` (the `0/255/256` sentence) from the «Три чашки света» slide. Slide 2 keeps its "light adds up, not paint" message; the numeric-steps message now lives only on the new slide. Check that Slide 2 still fills the 1280×720 canvas after removal (see §9.2).

## 6. Interaction & technical specification

### 6.1 New component: `app/src/js/lightswitch.js`
One small module, no framework. Proposed API:

```js
import { createColorStore } from './state.js';

// value = 0 | 255 only. The store is the source of truth.
export function createLightSwitch({ mountEl, store, stepsEl, valueEl, captionEl }) {
  // renders the toggle (if markup is not provided) OR binds to provided elements
  const unsubscribe = store.subscribe(({ r, g, b }) => {
    const isOn = r > 0 || g > 0 || b > 0;
    // update switch aria-checked, knob position, label Вкл/Выкл
    // update valueEl (0 / 255), captionEl (свет выключен / ярче всего!)
    // move stepsEl marker to the corresponding end
  });

  function toggle() {
    const { r, g, b } = store.get();
    const isOn = r > 0 || g > 0 || b > 0;
    if (isOn) store.setRGB(0, 0, 0);
    else store.setRGB(255, 255, 255);
  }

  // click/tap, Space/Enter (button default), pointer events (see §6.3)
  return { toggle, destroy() { unsubscribe(); /* remove listeners */ } };
}
```
- Keep the ON/OFF decision rule **store-derived** (`any channel > 0`) so it also behaves sensibly if a future slide pre-loads a color.
- Export small pure helpers for unit tests (see §8): `nextSwitchValue(current) → 0 | 255` and `isLightOn({r,g,b}) → boolean`.

### 6.2 Wiring in `app/src/js/main.js`
Add one branch in `initSlide(slide)` (pattern matches existing slides):
```js
// Slide: on/off switch
const switchEl = slide.querySelector('[data-light-switch]');
if (switchEl) {
  const store = createColorStore({ r: 0, g: 0, b: 0 });
  activeComponents.push(createBulb({ mountEl: slide.querySelector('[data-bulb-switch]'), store }));
  activeComponents.push(createLightSwitch({
    mountEl: switchEl,
    store,
    stepsEl:   slide.querySelector('[data-steps-scale]'),
    valueEl:   slide.querySelector('[data-switch-value]'),
    captionEl: slide.querySelector('[data-switch-caption]'),
  }));
}
```
- Registered in `activeComponents`, so `cleanupComponents()` on `slidechanged` tears it down like every other slide. No global state, no leak.

### 6.3 Keyboard — do not fight reveal.js (extends the existing capture)
- The switch is a `<button>`, so **Enter** and (usually) **Space** activate it natively. **But Reveal.js also uses Space / → / ← for navigation.** Solution: mirror the cup behavior in `setupKeyboardCapture()`.
  - Extend the existing capture `keydown` handler: when `document.activeElement` matches `.light-switch` (or any element inside `.switch-slide` that opted in), capture `Space`, `Enter`, and — only if the optional stepper is focused — `←`/`→`, and call `preventDefault()` + `stopImmediatePropagation()`.
  - `Escape` blurs and releases capture, exactly as for cups.
  - The slide always has on-screen controls and mouse/touch, so the child is never trapped.
- Reuse the existing `.focus-hint-banner` (`#focusHint`) or add a slide-local hint: «Пробел — включить/выключить · Esc — к слайдам». Prefer a **slide-local** hint here so the global banner is not overloaded; keep it inside the section.
- **Acceptance:** with the switch focused, Space toggles and the slide does **not** advance; with nothing focused, Space still advances the deck.

### 6.4 Pointer/touch
- Single `click` handler is enough for a button (pointer events synthesize `click` for touch). Do **not** add `setPointerCapture` here — no dragging is needed.
- Prevent double-fire on fast taps: guard with a small timestamp or rely on native `click`.

### 6.5 Reduced motion
- The glow "pop" on toggle is a CSS transition guarded by
  `@media (prefers-reduced-motion: reduce) { transition: none; animation: none; }`.
- The bulb's opacity change may be instant in reduced-motion mode (no fade).

### 6.6 Copy/i18n
- Even though the current codebase keeps most strings inline in `index.html`, the new JS component also needs a few strings (`свет выключен`, `ярче всего!`, `Вкл`, `Выкл`). Put them in `app/src/js/i18n.js` (which today is a 4-line stub) under a single `ru` dictionary, or pass them as `data-*` attributes from the markup. **Recommendation:** pass them as `data-*` (`data-label-on`, `data-label-off`, `data-caption-on`, `data-caption-off`) so all Russian copy stays visible in `index.html` and translators have one file to read.

## 14. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Space is captured globally, breaking slide navigation | Capture **only** while the switch (or optional stepper) has focus, using the existing focus-scoped pattern; `Esc` releases. |
| Toggling only 0↔255 feels too shallow ("just a switch") | The 256-tick ladder + pill + the aha sentence carry the lesson; add the optional `±1` stepper if the child wants to explore the middle 254. |
| Slide becomes crowded next to the Playground | Two-column layout with a strict content budget; verify with screenshots; the ladder is decorative and can shrink. |
| Copy drifts back onto Slide 2 (duplication) | S2 is an explicit acceptance item; grep for «256 шагов» and confirm it appears only on the new slide. |
| The new slide (and existing interactive slides) inherit the stale-centering bug | S0 is a hard prerequisite; verify with §2A.7 before building S1–S10. |
| A `ResizeObserver` relayout causes an observer loop / jank | `Reveal.layout()` only writes `top`, never `height`; debounce with `layoutQueued` + `requestAnimationFrame` (§2A.4). |
| Relayout is called too early (widgets still settling) | Double pass: immediate `Reveal.layout()` + one on the next `requestAnimationFrame`; the `ResizeObserver` catches anything later. |
| New store/global leaks across slides | Follow the `activeComponents` + `cleanupComponents()` lifecycle; no module-level mutable state in `lightswitch.js`. |
| Reveal fragment/step interactions fire the toggle twice | Use a native `<button>` `click` only; no pointerdown+touchend double binding. |
| Offline/package regression | No new dependencies; `npm run package` + `verify:web` unchanged; re-run the browser matrix (§12.11). |
